## 2. 핵심 학습 (개념 정리)

### 가변 인자 템플릿 등록 (BT 4.x)

ROS 노드 핸들이 필요한 BT 노드는:

```cpp
factory.registerNodeType<Approach>("Approach", node);   // 추가 인자 전달
// → Approach(name, config, node) 빌더 자동 생성
```

다른 BT 노드(SafetyCheck, IdleScan 등)는 ROS 무관이라 그냥 `registerNodeType<T>("T")`. 같은 factory에 혼재 가능 — 호출별 인자 다름.

### 안전 로직은 Nav2 의존성과 분리

Step C+D 진행 중 발견한 설계 함정:
- **초기 설계**: Nav2 fallback 분기에서 즉시 return → Proxemic/abort 코드에 도달 못 함
- **수정 설계**: Proxemic 계산 + abort 체크는 Nav2 모드 진입 전에 수행

이렇게 하면:
- 검증 환경(Nav2 없음) — abort 동작 확인 가능
- 운영 환경(Nav2 있음) — 동일한 안전 보장
- 안전(abort)이 통신 인프라(Nav2)에 종속되지 않음

### onStart vs onRunning abort

- `onStart` abort: 첫 진입 시 손님이 이미 1.0m 이내 → 호객 시도 자체 차단
- `onRunning` abort: 진입 중 손님이 1.0m 이내로 들어옴 → 진행 중인 Nav2 goal cancel + FAILURE

둘 다 필요. tick마다 거리 검사하면 100ms 응답성으로 abort 가능.

### Proxemic 변환 수학 (단순화)

로봇 = 원점 (0, 0), 고객 = (cx, cy):
```
dist = sqrt(cx² + cy²)
unit_to_robot = (-cx/dist, -cy/dist)
goal = customer + social_distance × unit_to_robot
     = (cx - cx/dist · 1.5, cy - cy/dist · 1.5)
```

Phase 2/4에서 TF 통합 시 (rx, ry)를 base_link → map TF로 정밀화.

### BT 사이클 자동 재시작

`tickOnce()` 매 100ms 호출 시:
- root_fallback이 SUCCESS 또는 FAILURE 반환 → BT 다음 tick에 자동으로 IDLE → RUNNING 전환
- 호객 funnel이 계속 돌아가는 본질에 적합 (한 손님 끝나면 다음 손님 후보 탐색)

## 3. 발견 / 위험 요소 / 갭

### 발견

- **첫 onStart는 publisher 도착 전 비동기 이슈**: Approach 구독자가 막 생성된 시점이라 첫 사이클은 customer_pose 도착 전 더미 사용. 두 번째 사이클부터 정상 Proxemic 계산. ROS2 pub/sub 기본 동작 — 의도된 비동기 지연.
- **`exposure_dynamic_framerate=ON` 영향 미검증**: 노트북 카메라(Bison 5986:211b)의 자동 노출이 fps에 영향. ROS2 v4l2_camera_node 시점에 OFF 권장 (이미 카메라 architecture doc §2.2에 기록).
- **fake publisher 종료 누락**: bash background kill 후 즉시 다음 명령 실행 시 publisher 잔재가 다음 테스트에 오염. `pkill -f` + `sleep 1`로 명시적 정리 필요.

### 위험 요소

- **로봇 위치 = 원점 가정**: Step C/D 단순화. Nav2 실제 통합 시 base_link → map TF 사용해야 정확한 Proxemic 좌표. Phase 2/4에서 정밀화.
- **onStart마다 wait_for_action_server 1초**: 검증 환경(Nav2 없음)에선 매 사이클 1초 누적 지연. 운영 환경에선 첫 호출 후 즉시 통과. 그래도 검증 효율을 위해 첫 사이클 시 한 번만 시도하도록 캐시 검토 가능 (필요시).
- **abort 반복 발화**: 손님이 1.0m 이내에 머물면 매 100ms마다 abort 로그. 정상 동작이지만 로그 스팸. 운영 시점에는 rate-limited 로깅 검토.

### 갭 (계획서 W2 명세 vs 실제)

- 계획서 line 163 "천장 카메라 pose_server" → 실제 **`/customer_pose` (PoseStamped) — 개발은 fake publisher, 운영은 카메라 2 (RPC-20F)**
- 계획서엔 BatteryCheck 통합이 W2 명세에 없는데 W1 SafetyCheck 골격에서 처리 보류 → Phase 1 W3 또는 Phase 2 안전 통합 시점에 다룰 것
- TF 통합 미완 (로봇 원점 가정으로 단순화) → Phase 2/4에서 정밀화
