## 1. 작업 흐름 (시간순)

### Step 0: 정렬 결정

- **엔진**: edge-tts. 다른 팀원이 LLM/TTS 조사 중 → **추후 변경 가능성 염두**.
- **격리 전략**: 엔진은 `tts_node.py` 한 파일에 캡슐화. 인터페이스(메시지/토픽)는 엔진 중립적으로 작성. abstraction 레이어는 미도입 (premature). 교체 시 변경 범위: `tts_node.py` + persona YAML voice 섹션 + requirements.txt + CLAUDE.md §7.
- **페르소나-voice 매핑**: 한국어 voice 3종(SunHi/InJoon/HyunsuMultilingual) × rate/pitch로 4 페르소나 차별화.
- **interrupt vs queue**: interrupt — BT abort 시 즉시 끊겨야 자연.

**중요 정정** — Microsoft Azure TTS는 한국어 voice 9종이지만 무료 edge-tts API에는 **3종만**:
- `ko-KR-SunHiNeural` (여)
- `ko-KR-InJoonNeural` (남)
- `ko-KR-HyunsuMultilingualNeural` (남, 다국어)

이전 검토 시 9종이라 잘못 알았음. 3종으로도 페르소나 4 차별화 가능 (rate/pitch 보강).

### Step 1: edge-tts 설치

```bash
pip install --user edge-tts==7.2.7
```

EyeCon v3.5 검증 버전. transitive 의존성(aiohttp, yarl, multidict, frozenlist 등)은 ROS와 충돌 없음 — mediapipe 때처럼 numpy/cv2 cleanup 불필요.

격리 셸 검증: `rclpy + edge_tts(7.2.7) + pygame` 모두 import 정상, numpy 1.26.4 + cv2 4.6.0 그대로.

### Step 2: UtterRequest.msg

```
std_msgs/Header header
string text         # 발화할 텍스트
string voice        # 엔진별 voice ID
string rate         # 속도 hint (엔진별 형식)
string pitch        # 피치 hint
string persona_id   # 디버깅
string stage_id     # 디버깅
```

voice/rate/pitch는 **엔진 중립적 string**. v1은 edge-tts SSML 형식. 미래 엔진(piper 등)으로 교체 시 같은 메시지/토픽 그대로 두고 tts_node 구현만 변경. CMakeLists.txt에 등록.

### Step 3: 페르소나 YAML 4종 voice 추가

```yaml
# generic.yaml

  rate: "+0%"
  pitch: "+0Hz"

# casual_browser.yaml — generic 상속, rate만 override
```

deep_merge가 voice dict에도 잘 적용됨 — friendly_child는 voice.name을 명시 안 했지만 generic의 SunHi 상속.

### Step 4: persona_manager 변경

`/dialog/utter` 발행 타입 `String → UtterRequest`. 새 헬퍼 `_pick_voice()`로 페르소나의 voice dict 가져옴. phrase + voice + face가 같은 콜백에서 발행 → 시청각 채널 동기화 보장.

```python
utter = UtterRequest()
utter.text = phrase
utter.voice = voice.get('name', 'ko-KR-SunHiNeural')
utter.rate = voice.get('rate', '+0%')
utter.pitch = voice.get('pitch', '+0Hz')
utter.persona_id = self.current_persona_id
utter.stage_id = stage_id
self.pub_.publish(utter)
```

### Step 5: tts_node.py

EyeCon `utils/tts_engine.py` 패턴 차용:
- `edge_tts.Communicate(text, voice, rate, pitch)` → `await comm.save(mp3_path)`
- `pygame.mixer.music.load(mp3) + play()`
- `asyncio.run(_synth(...))`을 별도 thread에서 (ROS spin 차단 없음)

**interrupt 정책 구현** — `_gen` 카운터로 stale 합성 폐기:
```python
with self._lock:
    self._gen += 1
    my_gen = self._gen
if pygame.mixer.music.get_busy():
    pygame.mixer.music.stop()  # 진행 중 재생 즉시 중단
threading.Thread(target=self._synth_and_play, args=(..., my_gen)).start()
```
합성이 끝났을 때 `my_gen != self._gen`이면 후속 utter가 들어왔다는 뜻 → 재생 폐기. 이로써 빠른 연속 utter 시 마지막 것만 재생.

견고한 main() 패턴 + destroy_node()에서 mixer.quit() + tempdir 정리.

### Step 6: 빌드 + 검증

빌드: msgs 4.93s + dialog 1.36s 통과. UtterRequest 타입 등록 확인.

## 2. 핵심 학습 (개념 정리)

### `env -i` 격리 셸과 audio device의 함정

ROS 빌드 검증 시 `env -i HOME=$HOME PATH=/usr/bin:/bin bash --noprofile --norc`로 환경 격리하면 colcon prefix chaining 문제는 해결되지만, **audio 관련 환경변수도 같이 누락**됨:
- `XDG_RUNTIME_DIR` (PulseAudio 소켓 경로)
- `PULSE_SERVER`
- `DBUS_SESSION_BUS_ADDRESS` (PipeWire/PulseAudio 발견)

이 변수들이 없으면 SDL/pygame이 ALSA로 직접 시도 → `ALSA: Couldn't open audio device: Host is down`. ALSA는 단일 프로세스 점유 모델이라 데스크톱 PulseAudio가 점유 중이면 새 프로세스가 못 엶.

**해결**:
- 빌드 단계: `env -i` 사용 (audio 무관, colcon 격리 우선)
- 실행/검증 단계 (audio 필요): 일반 `bash --noprofile --norc` 또는 그냥 일반 셸. ROS source만 명시.
- 또는 `env -i ... XDG_RUNTIME_DIR=$XDG_RUNTIME_DIR PULSE_SERVER=$PULSE_SERVER ...`로 audio 변수 명시 전달.

기록 위치: 본 회고 + CLAUDE.md §7 (필요시 추후 정리).

### edge-tts 한국어 voice 실제 가용 수

이전 검토에서 9종 가정했으나 **무료 edge-tts API에는 3종만**:
1. SunHi (여)
2. InJoon (남)
3. HyunsuMultilingual (남, 다국어 — 영어/일본어 혼합 가능)

Microsoft Azure 유료 TTS에는 더 많지만 (Bong-Jin, GookMin, JiMin, SeoHyeon 등) edge-tts 무료 API는 제한적. **rate/pitch 조합으로 보강**하면 4 페르소나 차별화는 충분.

추가 voice가 필요해지면:
- HyunsuMultilingual을 4번째 voice로 활용 (다국어 페르소나용)
- 또는 Azure 유료로 전환
- 또는 다른 엔진(piper)으로 교체 (사용자 의도)

### 인터페이스 안정성 + 구현 격리

UtterRequest 메시지/토픽은 엔진 중립. tts_node 한 파일이 엔진 의존성 캡슐화. 미래 LLM/TTS 변경 시:
- **변경**: tts_node.py 재구현, persona YAML voice 섹션, requirements.txt
- **불변**: UtterRequest.msg, /dialog/utter 토픽, persona_manager, BT 노드, face_avatar

abstraction 레이어 (engine.synthesize() 추상 함수)는 v1에 미도입. 이유: 엔진 1개일 때는 over-engineering. 2개 이상 동시 지원 필요해지면 그때 도입.

### interrupt 정책의 generation counter 패턴

비동기 작업(edge-tts 합성)이 진행 중일 때 새 작업이 들어오면 stale 결과를 폐기해야 함. 일반적 패턴:

```python
with lock:
    self._gen += 1  # 새 작업 번호
    my_gen = self._gen
... 비동기 작업 ...
with lock:
    if my_gen != self._gen:
        return  # stale — 후속 작업이 들어옴
... 결과 사용 ...
```

ROS 노드의 콜백/타이머/외부 API 응답 처리에 일반화. lock + atomic counter면 충분 (lock-free 큐 등 복잡한 구조 불필요).

### asyncio + threading + ROS spin 통합

edge-tts는 async API. ROS spin은 별도 메인 루프. 두 이벤트 루프를 한 노드에서 운영하려면:

- **방안 A** (선택): `threading.Thread`에서 `asyncio.run(coro)` 호출. async가 thread-local. 단순.
- 방안 B: rclpy.executors.MultiThreadedExecutor + asyncio. 복잡.
- 방안 C: nest_asyncio로 동일 루프 강제. 권장 안 함.

방안 A는 EyeCon 패턴. 합성 1건마다 short-lived thread → 비용 무시 가능. async가 thread 내부에서 완전히 닫혀 ROS spin과 격리.

## 3. 발견 / 위험 요소 / 갭

### 발견

- **persona_manager의 단일 콜백에서 phrase + face + voice 동시 발행**: 시청각 채널 완벽 동기화. 같은 callback에서 publish하므로 race 없음. ROS DDS 타이밍 차이는 ms 수준이라 사용자 체감 동기화.
- **edge-tts 첫 호출 latency**: ~200~300ms (Microsoft 클라우드 첫 연결). 후속 호출은 ~100ms. BT funnel이 빠르게 진행되면 첫 utter가 약간 늦게 나오나 자연스러움.
- **deep_merge가 voice dict도 깊이 머지**: friendly_child가 voice.name을 안 적었는데 generic의 SunHi 상속 + rate/pitch만 override. Phase 1 W3에서 만든 _deep_merge가 face_expression / phrases / voice 모두에 일관 작동.

### 위험 요소

- **인터넷 의존**: edge-tts는 Microsoft 클라우드. 카페 wifi 끊기면 전체 호객이 침묵. 운영 시 네트워크 모니터링 또는 오프라인 fallback (piper 등) 필요. Phase 후속.
- **edge-tts 무료 API 정책 변경 위험**: Microsoft가 무료 종료 또는 rate limit 강화 가능. 다른 팀원의 LLM/TTS 결정에 영향 큼.
- **외래어/메뉴명 발음**: 현재 phrase는 한글 표기("디카페인", "시그니처 라떼")라 안전. 새 페르소나/메뉴 추가 시 영문 직접 표기 금지 (Step 0 평가 참조).
- **interrupt 정책의 BT 동기화 갭**: BT가 utter 직후 다음 stage로 진행하면 발화가 잘림. 현재 BT 노드(IceBreak/Offer/LeadIn)는 stage_id publish 즉시 SUCCESS 반환 → 발화 완료 안 기다림. **TTS 발화 완료 신호가 BT로 돌아오는 메커니즘 없음**. Phase 후속에서 IceBreak가 `/dialog/utter_done` 같은 신호 대기하도록 변경 검토.
- **mp3 임시 파일**: tempdir에 1개. 짧은 시간 내 두 utter 시 파일 동시 쓰기 가능. _gen counter로 stale 폐기하지만 파일 쓰기 중 race 가능성. 실 환경에선 거의 발생 안 함.
- **edge-tts의 한국어 voice 수**: 3종만 가용. 페르소나가 5종 이상 늘어나면 voice 차별화에 한계. rate/pitch만으로는 voice character가 동일.

### 갭

- **TTS 발화 완료 신호**: 위 위험 참조. v1엔 미구현, Phase 후속 (`/dialog/utter_done` topic 또는 service).
- **phrase 내 SSML 직접 사용**: phrase YAML에 `<emphasis>`, `<break>` 등 SSML 태그 직접 사용 가능하나 v1엔 plain text만. 페르소나별 미세 표현 (강조, 정지) 추가 시점에 SSML 도입.
- **voice 변경 시 face_expression과 동시성**: 현재 phrase + face + voice 같은 callback이지만 face는 즉시 표시, voice는 200~300ms 후 발화 시작. 미세하지만 face가 먼저 나오는 부조화. Phase 후속에서 face delay 또는 utter pre-roll 검토.

```bash
# 일반 셸 (audio 환경변수 보존)
source /opt/ros/jazzy/setup.bash
source ~/moca/install/setup.bash

ros2 run dobi_npc_dialog tts_node &
sleep 1
ros2 topic pub --once /dialog/utter dobi_npc_msgs/msg/UtterRequest \
  "{text: '안녕하세요!', voice: 'ko-KR-SunHiNeural', rate: '+0%', pitch: '+0Hz'}"
```

### 페르소나 voice 차이 비교 (4 페르소나)
```bash
ros2 run dobi_npc_dialog tts_node &
ros2 run dobi_npc_dialog persona_manager &
sleep 2
for p in casual_browser friendly_child professional_adult generic; do
  ros2 service call /set_persona dobi_npc_msgs/srv/SetPersona "{persona_name: $p}"
  sleep 0.5
  ros2 topic pub --once /dialog/request std_msgs/String "{data: 'icebreak'}"
  sleep 4
done
pkill -INT -f "tts_node|persona_manager"
```

### 통합 (BT + persona + face + tts)
```bash
ros2 run dobi_npc_dialog tts_node &
ros2 run dobi_npc_dialog persona_manager &
ros2 run dobi_npc_dialog face_avatar &
ros2 launch dobi_npc_bt bt_executor.launch.py &
# (선택) ros2 run dobi_npc_emotion geva_node &
# (선택) ros2 run dobi_npc_emotion rapport_tracker &
```

### 좀비 정리
```bash
pkill -TERM -f "bt_executor|persona_manager|face_avatar|tts_node|geva_node|rapport_tracker"
sleep 1
pkill -KILL -f "bt_executor|persona_manager|face_avatar|tts_node|geva_node|rapport_tracker" 2>/dev/null
```
